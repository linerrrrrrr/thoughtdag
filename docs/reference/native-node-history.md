# API 聊天节点与 Codex 节点

未回答节点可以选择「API 聊天」。连接检测确认 Codex 有可用模型后，画布节点和右侧详情会显示「Codex」选项，模型列表按节点类型过滤。子节点默认继承父节点类型，也可以在发送前切换，因此同一条链可以混合两类节点。已回答节点展示执行类型，后续对话通过新子节点进行。既有其他运行时的导入节点保留原运行时。

API 节点继续使用按角色分开的聊天消息。Codex 节点先将已选上下文编译为 Responses 消息与工具记录，通过 `thread/inject_items` 注入；`turn/start` 只发送本轮问题及本轮图片。注入失败会报错，不会退回把整段历史拼进一个用户消息。

## 画布与原生历史

每个回答版本保存独立原生记录，包括线程 ID、轮次 ID、节点映射、条目区间、内容修订指纹、原始工具调用与结果、磁盘检查点。映射与画布一起持久化、导出和恢复。轻量检索索引只保留来源信息，不复制完整工具输出或图片。

画布已有的上下文顺序、引用、归档、附件选择和高亮过滤规则仍然生效。未编辑且完整捕获的 Codex 节点可以使用原始消息和成对工具记录；工具调用 ID 按节点分配命名空间，避免合并不同线程时冲突。工具记录只作为历史输入，不重新执行旧工具，也不会恢复以前工作目录的文件。

历史内容、问题、回答版本、图片或工具附件被编辑后，以当前画布选择为准。旧版本缺少原生记录时，不借用其他版本的工具历史。早期导入节点、无可读原始日志或含暂不支持条目的节点，只能将可见问答和已选执行记录作为结构化消息传递；界面会标明原生记录不可用。运行环境配置和隐藏推理不作为可迁移历史。

## 续聊与重建

续聊需要满足两层校验：

1. 本次画布历史的前缀与某个已选原生节点的已保存历史一致，工作目录也一致。
2. 后端确认该线程磁盘检查点和最后轮次没有变化，而且未被当前运行时占用。

通过后恢复同一线程，只注入新增的后缀。重启运行时后仍可使用持久化映射完成这两层校验。上游编辑、连接变化、外部追加会话、缺少检查点或线程占用时，新建原生线程并注入当前完整历史。新线程不继承旧线程的会话授权。

当前协议没有跨独立 app-server 进程的原子锁；后端在 resume 前后检查磁盘状态，但不承诺多个外部客户端同时写同一线程时的原子性。涉及材料目录提示等上下文变化时，可能选择重建而非续用原线程。

## 官方界面的边界

`thread/inject_items` 写入模型可见并可持久化的历史，但不会补造官方历史轮次。实际新执行的 Codex 节点成为官方轮次；API 节点以及重建时导入的旧节点由画布映射和展示。因此这里实现的是原生结构化上下文、原生新轮次和可靠的画布映射，不是官方界面完整复刻任意 DAG。

## 独立运行

Windows 桌面版内置 CLI 的 Registered Core 启动要求安装包身份，直接 spawn 时可能失败。现在的启动器优先独立 CLI；适用的 Windows 路径使用进程级官方 MXC 沙箱，保留原审批及工作区策略。详见 [运行时启动说明](codex-runtime-launch.md)。不支持 MXC 或原生注入的环境会明确失败，不关闭沙箱或改写全局设置。

## 2026-11-11 实测

使用实际前端上下文编译器、`agentCallStream` 和后端运行时，完成两次真实普通聊天 API 调用及三次真实 Codex 轮次：

| 检查 | 结果 |
| --- | --- |
| API A → Codex B | B 从注入历史恢复 A 的随机数和词，真实 shell 写入 `b-proof.json`，退出码 0 |
| B → API C | C 收到角色分开的上下文，计算结果正确 |
| 重启运行时 → Codex D | D 续接 B 的同一线程，只追加 C 的历史，真实 shell 写入 `d-proof.json`，退出码 0 |
| 修改 A 后创建 E | 创建新线程，E 回答修改后的数据 |
| 官方应用读取原线程 | 仅 B、D 两个原生轮次；A、C 未变成官方轮次 |
